# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Build Commands

- `npm run dev` - Start compilation in watch mode
- `npm run build` - Build production version (with TypeScript checks)
- `npm version patch|minor|major` - Bump version
- `npm run format` - Format code with Prettier
- `npm run format:check` - Check code formatting with Prettier (CI pins Prettier 3.6.2; if `npx prettier --version` differs, use `npx prettier@3.6.2` so a local `--write` doesn't reformat unrelated lines)
- `npm run lint` - Lint code with ESLint
- `npm run lint:fix` - Lint and fix code with ESLint
- `npm run typecheck` - Run TypeScript type checking
- `npm run test` - Run tests with Vitest
- `npm run test:watch` - Run tests in watch mode
- `npm run docs:dev` - Start VitePress documentation server
- `npm run docs:build` - Build documentation
- `task build` - Build and optionally copy to plugin directory (if PLUGIN_DIR is set)
- `task pr` - Prepare for PR (format, lint, type check, and test)
- `task release` - Release a new minor version (includes format, lint, type check, and test)

Recommended workflow: After running tests and fixing any issues, run `npm run build` to catch TypeScript or bundling errors that tests may not surface.

## Code Style

- **TypeScript:** Use strict typing (noImplicitAny, strictNullChecks)
- **React:** Use functional components with explicit props interfaces
- **JSX:** Use React JSX syntax with function components
- **Imports:** Group by: 1) external packages, 2) local files; sort alphabetically within groups
- **Naming:** PascalCase for components/classes/interfaces, camelCase for functions/variables
- **Types:** Define in lib/types.ts with explicit interfaces; use TypeScript generics where appropriate
- **Error Handling:** Use nullable types with default values or early returns; avoid unchecked nulls
- **Components:** Place reusable UI components in lib/components/; use props interfaces
- **Domain Logic:** Place domain-specific code in lib/domains/
- **Views:** Place UI views in lib/views/; extend BaseView where applicable
- **Formatting:** Use consistent indentation (2 spaces), trailing commas, and semi-colons
- **State Management:** Use React hooks (useState) for component state
- **CSS:** Prefix all styles with plugin namespace; place component styles in lib/styles/components/
- **File Structure:** Keep code aligned with domain separation (domains, components, views)

## UI Components (Storybook)

- **Story files** live in `stories/` and follow Storybook 9 conventions (import from `@storybook/react-vite`, test utils from `storybook/test`)
- **Run Storybook** with `npm run storybook` (uses portless for a stable URL)
- When working on components, read their source files in `lib/components/` and existing stories in `stories/` directly — do not rely on a Storybook MCP

## Architecture

- **Plugin Structure:** Obsidian plugin with React components for D&D UI elements
- **Code Block Processors:** Each View class processes specific YAML code blocks (ability, skills, stats, etc.)
- **State Management:** Uses KeyValueStore with JsonDataStore for persistent state across sessions
- **Component Architecture:**
  - Views: Handle code block parsing and rendering (extend BaseView)
  - Components: React components for UI elements
  - Domains: Business logic for D&D mechanics (abilities, skills, combat)
  - Services: KV store for state persistence and event bus for communication
- **Rendering:** Views register markdown post-processors that transform YAML into interactive React components
- **Plugin Settings:** Configurable color scheme and state file path in settings tab
- **Event System:** Uses message bus (msgbus) for communication between components and frontmatter changes
- **Frontmatter Integration:** Automatically syncs with Obsidian frontmatter for character data like proficiency bonus and level
- **View Registration Pattern:** Each view extends BaseView and implements:
  - `registerView()`: Registers code block processor with plugin
  - `render()`: Transforms parsed YAML data into React components
  - State persistence handled automatically via KV store integration
- **State Persistence:**
  - In-memory cache with automatic disk persistence
  - Scoped by view type and element ID
  - State file location configurable in plugin settings
- **Template System:** Handlebars-style templating for dynamic content (e.g., {{dex_mod}} in ability descriptions)
- **D&D Mechanics:** Implements 5e rules for ability modifiers, proficiency bonuses, skill calculations

## Testing

- **Framework:** Vitest with Node environment
- **Test Files:** Place tests alongside source files with `.test.ts` extension
- **Coverage:** Configured to exclude config files, main.ts, and build outputs
- **Running Tests:**
  - All tests: `npm run test`
  - Watch mode: `npm run test:watch`
  - Single test file: `npm run test path/to/file.test.ts`
  - Pattern matching: `npm run test -- --grep "pattern"`
- **Test Patterns:** Mock external dependencies (e.g., MockDataStore), use TypeScript generics for type safety

## Development Workflow

- **Plugin Development:** Set PLUGIN_DIR environment variable to auto-copy built files to Obsidian plugin directory
- **Vault:** The plugin repo holds no vault. Tests, stories, scripts, the simulators and the cloud Obsidian use the `testing-vault` repo, cloned beside this one (`../testing-vault`) or wherever `RPG_VAULT_ROOT` points. CI clones it the same way.
- **Documentation:** VitePress documentation in `/docs` with examples and component references
- **State File:** Plugin creates `.dnd-ui-toolkit-state.json` (configurable) for persistent component state

## Cloud Obsidian screenshots

`node scripts/cloud-obsidian.mjs start|screenshot|stop` runs real Obsidian headless (Xvfb + Electron, driven over CDP with Playwright) in cloud sessions. `start` downloads Obsidian once (cached in `~/.cache/rpg-obsidian`), copies the vault from `$RPG_VAULT_ROOT` into `~/.cache/rpg-obsidian/work/vault` (the real vault is never touched) and installs the built `main.js`/`manifest.json`/`styles.css`/`esbuild.wasm` — run `npm run build` first. The plugin runs with the settings in `scripts/cloud-obsidian.data.json` (a copy of the real `.obsidian/plugins/obsidian-rpg-ui/data.json` without its API-key fields; refresh it when the real settings change). `PLUGIN_DATA=<file>` uses another file; `PLUGIN_DATA=none` seeds a `data.json` with guessed system mappings instead. To lay a few settings over that file for one run, set `PLUGIN_SETTINGS` (a JSON file, or JSON) or `PLUGIN_SETTINGS_B64` (the line the plugin's Settings > General > Share settings > Copy button writes). Set `THEME_DIR` to a checkout of a theme repo (e.g. `/home/user/ddspog/obsidian-ribbons-theme`, containing `manifest.json` and a built `theme.css`) to install it too; the vault's `appearance.json` selects the active theme. With a theme, open fonts from `@fontsource` (npm) are mapped to the theme's `My Text/Title/Table/… font` names, since the macOS fonts it prefers (New York, SF Compact) are missing in the cloud; override with `FONT_SERIF`, `FONT_SANS`, `FONT_ROUNDED` (fontsource ids) or disable with `CLOUD_FONTS=0`. `prepare` pre-downloads Obsidian and fonts without launching it. Then `screenshot "<note path in vault>" out.png ["heading to scroll to"]` renders the note in reading mode, at 1600×1400 with Obsidian's file explorer collapsed (`KEEP_SIDEBAR=1` keeps it); view the PNG with the Read tool. `MOBILE=1 VIEWPORT=390x844` renders the note in Obsidian's phone UI (`is-mobile`, a 390px-wide window); mobile layout rules live in `lib/styles/mobile.css`. The first mobile run after a fresh `start` may show rule blocks as "Unknown" (esbuild-wasm fails to initialise in emulated mobile mode): open the note once without `MOBILE` so the system bundle is cached, then repeat. The `rpg-dev` CLI below needs the desktop Obsidian CLI and does not work against this headless instance.

`node scripts/perf-log-bench.mjs "<note path>" [runs] [--profile out.cpuprofile]` measures opening a note in that Obsidian (time to first content and to settled, long tasks, scroll frame times; `MOBILE=1 VIEWPORT=390x844` for the phone UI). The first run is a warm-up and is not counted. A `--profile` file lists by function in the usual way; build with `NODE_ENV` set to production and no minify to read it, or React's development build will dominate.

## PDF import

The command "Import PDF as compendium book" (`lib/plugin/pdf-import-modal.ts`) writes a PDF into the vault as a book: a note a chapter, tabs, `rpg table` and `rule.side` blocks, entries of a kind in folders, pictures in `_assets`. The work is in `lib/domains/pdf-import/` and has no Obsidian in it (`extract` reads a page with pdf.js, `layout` orders it, `blocks` types its lines, `structure` gathers chapters, `emit` writes notes, `entities` recognises spells, creatures, items, classes and the like and writes the plugin's blocks for them, `pipeline` runs them against a host). `node scripts/pdf-import.mjs book.pdf out --title "Name"` runs the same code from a terminal (pdfjs-dist, @napi-rs/canvas and tesseract.js from `node_modules`), made for a model to drive: `--json` streams each stage and ends with the result, `pages book.pdf 30,31` shows what the layout made of pages, and every import writes an "Import review" note and a report (`<out>/.pdf-import/<book>.json`, paged with `review <report>`) of what needs a person's judgement; `/pdf-import` (`.claude/commands/pdf-import.md`) is the workflow, `node scripts/pdf-import.mjs help` the reference; `PDF_IMPORT_DEBUG=1` prints heading looks, every block and every entity found; `--system tales-of-the-valiant` treats the out folder as a vault and files the book into that system's `compendium` (on a shelf with `--shelf rules|tables|builders|settings`: the game's rules and options, oracle and random-table books, campaign builders, and worlds) and its entities into `worldbuilding` (`organise.ts`), never over a note that exists. Two books set unlike each other are the yardstick for a change: the Player's Guide and the 5e SRD 5.1 (`media.wizards.com/2023/downloads/dnd/SRD_CC_v5.1.pdf`); run both and compare the entity counts before and after. Books of tables have a yardstick of their own: four adapted by hand in the testing vault (the Nomicon, the Tome of World Building, the Tome of Adventure Design, the Solo Adventurer's Toolbox; the PDFs are the owner's and are not in a repo), measured with `node scripts/pdf-import-compare.mjs <import folder> <vault folders…> [-v]` (captions found, same row count, rollable; the figures to beat are in `docs/pdf-import.md`). `pages` (or `PDF_IMPORT_PAGES=30,31` on an import) prints what the layout made of those pages; a run over a few pages (`--from`/`--to`) finds other columns and furniture than the whole book does, so debug on the whole book. Try a change on a real book that way before the cloud Obsidian. Obsidian's pdf.js is 4.9. See `docs/pdf-import.md`.

## Working with the repository owner

- **Questions as artifacts.** When a question comes down to a choice that is visual or behavioural (a layout, a default, a flow), do not ask it in prose. Publish an artifact with the problem shown on real screenshots and the options as mockups to choose between, mark a recommendation, and end with a "Copy picks" summary to paste back. The owner liked this far better than text questions.
- **`/ui-review <goal> [scope]`** (`.claude/commands/ui-review.md`) runs a whole review: picks real example notes from `docs/ui-review/` (the curated set and the generated `block-census.md`), captures them on a phone and a desktop (`scripts/ui-review-capture.mjs`), runs the Impeccable analyses, and builds a before/after board to rate (`scripts/ui-review-board.mjs`). With no goal it shows every analysis Impeccable can run and lets the owner choose.
- **Design reviews.** For UI reviews the owner uses Impeccable (`npx skills add pbakaus/impeccable -g -a claude-code -s '*' -y --copy`): a design-review agent and a detector-and-measurement agent run independently, on phone then desktop, and their findings are merged. Verify any headline claim in the live app before reporting it.

## Simulators

`simulators/` is a sub-project for trying single pieces of the plugin in a browser (a phone included): each simulator is one HTML file holding the plugin code it exercises, `styles.css` and a copy of the vault's notes, with `obsidian` stubbed. `npm run build`, then `RPG_VAULT_ROOT=/path/to/vault npm run sim:build [id]` writes `simulators/dist/<id>.html`; `npm run sim:check` opens each in headless Chromium; `npm run sim:new <id>` scaffolds one. Shared code is in `simulators/core/`, each simulator in its own folder (`lonelog-log`: the Log and its cards; `rpg-table`: a table block). See `simulators/README.md` for the API and for what is not simulated (character sheets, other plugins, images).

## rpg CLI and the LLM Game Master

`npm run build:cli` writes `cli/dist/rpg.cjs` (sources in `cli/rpg/`): the plugin's own code run against a vault on disk (`--vault`, `$RPG_VAULT`, else the vault the plugin sits in). `rpg character|log|map|lookup|search` read. `rpg gm …` lets a model run a session as its Game Master: `guide` (the orientation, `cli/rpg/gm/guide.md`), `brief`, `cards`, `play` (a GM Screen card, dice rolled in the CLI and written at once, to the log or to a prep draft), `roll`, `say`, `consult`, `prep`, `note`, `mode secret|open`, `reveal`. `rpg session manifest|fork|switch|lines|save|pack|unpack` keeps a session's lines of play under `.rpg-sessions/`. `/gm <session>` (`.claude/commands/gm.md`) starts a GM. Try a change on a copy of the vault, never the checkout: `rpg gm` writes the session note. See `docs/game-master.md`.

The **GM link** (off by default: `gmLinkEnabled`, Settings › General › GM link) lets the player stay in Obsidian (a phone too) while the GM is elsewhere: the plugin (settings, General › GM link; `lib/plugin/gm-link.ts`, `lib/domains/gm-link/`, `lib/services/github-relay.ts`) commits the session's play notes to a branch of the vault's GitHub repository on **Hand over** and writes the GM's changes back when the turn returns. The GM's end: `rpg table link <session> --pr N` (the link the player pastes), `git pull`, `rpg table take <session>`, play, `rpg table give <session> --note "…"`, commit and push. How the GM runs the session (secret or open, how far a turn goes, what to ask first, a profile note) is set from a dialog and kept in the session note's properties (`lib/domains/gm-link/prefs.ts`); `rpg gm brief` prints it. See `docs/gm-link.md`.

**Improve the wording** (`lib/domains/session-log/reword.ts`, `lib/plugin/reword-modal.ts`): passages of a log picked in a dialog, reworded by the Anthropic endpoint of the settings, reviewed, then written; only a passage's words change, never its tags, links or any other line. See `docs/reword.md`.

## rpg sim (encounter simulator)

`rpg sim run --monster "<note>[:<count>]"… [--pc <note>]… [--seed N] [--trials N] [--rounds N]` runs a seeded Monte Carlo of a party (default: the four level-1 PCs under `tales-of-the-valiant/adventuring/characters/`) against bestiary notes and prints one JSON document (win/TPK/stalemate rates, per-trial rounds and HP, per-PC KO rate, the ToV difficulty label, and a `fidelity` section saying which spells, attacks and features were modelled or skipped). `rpg sim suggest [--difficulty easy|challenging|deadly] [--habitat H] [--type T] [--cr C] [--limit N]` sweeps the bestiary for single-kind groups near the ToV benchmark and ranks them. `--rank outcome` ranks `suggest` candidates by the simulated outcome (`avgHpLost`, `tpkRate`) against the difficulty's profile (`lib/domains/encounter-sim/fit.ts`, tunable heuristics) instead of by total CR, and widens the sweep (total CR up to 4 x the benchmark, at most 30 of a kind, a kind's counts stop once `tpkRate` >= 0.9); every candidate carries `avgHpLost` and a `fit` (`fit`, `too-easy`, `too-hard`) in either mode. `--base "<note>[:<count>]"` (repeatable, `suggest` only) keeps groups in every fight and sweeps one more kind added to them (`base` on each candidate, total CR includes it). **Tiers:** a party is profiled by `lib/domains/encounter-sim/party-profile.ts` (size, average level, tier of play 1–4, benchmark, and the single-monster CR range of the Monster Vault's Challenging Benchmarks table). `--tiers same|lower|all` (default `same`) keeps `suggest`, `plan` and `catalog check|suggest` to the party's tier: a catalog entry by its `tier-N` tags, an untagged entry or a swept monster by the max single-monster CR (`lib/domains/encounter-catalog/tier.ts`, `cli/rpg/sim/tier-scope.ts`); `lower` adds lower tiers for story use (marked `belowTier`), and `catalog list` shows every tier unless `--tiers` is written. `suggest` ranks by outcome by default (`--rank cr` for the old order). `rpg sim --help` lists every flag; sim usage errors exit 1, runtime errors 2. The engine is pure (`lib/domains/encounter-sim/`: rng, difficulty, monster-actions, spell-actions, engine, montecarlo); the vault-facing loaders and commands are in `cli/rpg/sim/` (`rpg` hands everything after `sim` to `cli/rpg/sim/index.ts`, which has its own strict flag parse). Specs in `cli/rpg/sim/` build a fixture system and, when `../testing-vault` is there, run over a copy of it (`test-support.ts`).

`rpg sim calibrate [<session note or folder>…]` (`cli/rpg/sim/calibrate.ts`, read-only) sets each fight a session log records (`[COMBAT]`…`[/COMBAT]`, its `[F:…]` foes, the note's `pcs`) against the simulator's run of it: HP lost, rounds, knockouts, the real fight's `percentile` among the simulated; under 10 fights it says not to tune the profiles. `catalog check` re-runs a fit near its edge (`fitMargin` in `fit.ts`: within two standard errors of the tolerance) with four times the trials and marks it `borderline`. The engine uses a "(Recharge 5-6)" action once until a d6 brings it back, "(N/Day)" N times, and sizes an area by the targets-in-area table (`areaTargets`, `useLimitOf` in `monster-actions.ts`). Conditions ride on actions (`Inflict` in `types.ts`: the PC sheet's `inflicts`, read by `inflictOfSheet` in `cli/rpg/sim/party.ts`; a monster's prose by `inflictOfHit`/`inflictOfSave`) and are played as advantage, disadvantage and lost turns; a PC's sheet `rider` is a `DamageRider` (mark or once a turn); Two-Weapon Fighting adds the off-hand swing; monsters focus the most hurt PC for `MONSTER_FOCUS` (0.5) of their picks. Monster resistances, immunities and vulnerabilities (and condition immunities) apply (`lib/domains/encounter-sim/defences.ts`, named "… Resilience" traits read from their text); a damage-free control spell the sheet gives a condition and a save is a save action (`controlSpell` in `party.ts`); a bonus-action heal (`HealAction.bonus`, from the spell's `casting:`) comes on top of the action; a heal is also read from a spell's text. A spell note with no `roll:` is read through `deriveSpellRoll` (`lib/domains/spells/derive-roll.ts`: attacks, saves, areas, conditions, heals, riders, `leveled` and `upcast`); `rpg sim spells [--write]` (`cli/rpg/sim/spells.ts`) writes those rolls into the spell notes, under a comment to delete once checked, never over a written `roll:`. Legendary actions (`legendary` features: an attack or save, or "makes a Tail attack", with their cost) are spent after other creatures' turns from 3 points a round (`LEGENDARY_POINTS`, `CombatActor.legendary`); monster saves read both "Dexterity saving throw" and the Monster Vault's "DEX save". Buffs and debuffs (Bless, Bane, Shield of Faith: a die to attacks and saves, or AC, on allies or enemies) are `BuffAction`s read from a spell's text by `buffFromText` and cast when worth more than an attack (`BUFF_WORTH` in `engine.ts`). A monster's Spellcasting list (`parseMonsterSpellcasting` in `monster-actions.ts`) is resolved against the vault's spell notes (`monsterSpells` in `cli/rpg/sim/monsters.ts`: numbers from its stated DC and CR, "N/day" as a use limit, no slots). `--brief` (on `run`, `suggest` and `catalog suggest`) prints the short form a model reads: groups as `--monster` takes them (`"Thug:3"`), no per-trial arrays or statblock summaries, one item to a line (`cli/rpg/sim/brief.ts`); `run --brief` adds the fit for each difficulty and what was skipped that may matter. `rpg sim plan [<theme words>] [--habitat H] [--tag t]… [--limit N]` is the one call a Game Master model makes: the party's catalog first (its current `fit` entries, confirmed before drafts, theme words and habitat matched loosely), then a `suggest --rank outcome` sweep to fill `--limit` (3) options, with `notes` on what to do next; read-only (`cli/rpg/sim/plan.ts`). `rpg gm guide` has a "Building an encounter" section that points the GM at `plan` and `run --brief`.

`rpg sim catalog init|draft|add|confirm|remove|tag|use|prepare|adjust|session|check|suggest|list` keeps an **encounter catalog** per party: a vault note (default `<system>/gm-tools/encounter-catalog/<party>.md`, one `yaml encounter` block per entry, editable by hand; model in `lib/domains/encounter-catalog/`, commands in `cli/rpg/sim/catalog*.ts`) of ready encounters, each stamped by the simulator `fit`, `too-easy` or `too-hard` for the party. `draft <note-or-folder>` reads random-encounter table rows into draft entries (a dry run that writes nothing unless `--accept`, which takes only `--min-confidence` and up, default high, or the reviewed ids of `--only <id>`; each draft shows its `scene` and `reasons`; the rules of `lib/domains/encounter-catalog/extract-row.ts` are listed under "Known limits of the extraction" in the docs); other names for bestiary notes are kept in `<system>/gm-tools/encounter-catalog/Bestiary aliases.md` (`cli/rpg/sim/aliases.ts`), read by `draft` and by every `--monster`, which also takes a note's spoken name ("Goblin"); `check` simulates the entries that have no fit or whose party stamp, difficulty or session interval changed; `suggest --tag forest` is the cheap read a Game Master model makes (confirmed, current `fit` entries only; `--refresh` checks first). `use <id>` records a run (`suggest` and `plan` hold it back for `reuseAfterSessions`, default 3); `session` counts the party's session notes in the vault (or sets one); `tag` adds and drops tags. Entries keep the table row's words (`source.text`, printed as `scene`), a rolled count is also checked at its fewest and most (`fit.atMin`/`atMax`), and tags match plural or not (`lib/domains/encounter-catalog/words.ts`). `suggest --fit <state>` keeps only those fits; a party with a CR benchmark of 0 gets a `note` saying why nothing is suggested. In Obsidian the note's `rpg encounter-catalog` block (body `view: encounter-catalog`) renders the board: party header and tier chips, a fit strip, filters and a card per encounter with a gauge of HP lost against the aim; Confirm and Tags write the note through the same model; Prepare writes a `[Enc:[[catalog#^id|Name]]|foes|prepared]` Lonelog line to the party's latest session note (`catalog prepare` from the CLI; `lib/domains/session-log/prepared-encounter.ts`), which Start Combat offers above its foes; starting the fight appends the tag `fought S02` and, on Save, records the run in the catalog (`lib/views/EncounterCatalogView.tsx`, `lib/components/encounter-catalog/`, `lib/domains/encounter-catalog/board.ts`, styles in `lib/styles/components/encounter-catalog.css`). Each entry is an `rpg encounter` block shown as one line, kept in a folded callout ("N entries as written") under the board. Prepare offers Undo on its notice, a prepared card shows where and Unprepare; run encounters rest at the end of the board until `reuseAfterSessions` pass; only the best-fitting draft's Confirm is highlighted. The board does not simulate: it reads the `profile` (size, level, tier, benchmark, single CR, stamp) `catalog check` writes to the frontmatter. The CLI writes the note through `cli/rpg/write.ts` `writeNote` (it backs the old text up); the e2e spec uses a temp copy of the vault. `adjust [<id>…]` tries changes on entries that do not fit (counts, equivalent swaps of the same kind of creature, rank-and-file minions or a leader, a group less; a second change when none fits) against the party, ranks the fitting ones and adds tactics in words; `--accept [--pick N]` adds the best as a draft with `adjustedFrom`/`adjustment` (`lib/domains/encounter-catalog/adjust.ts`, `cli/rpg/sim/catalog-adjust.ts`). See `docs/encounter-catalog.md`.

**Building encounters** (`rpg sim build [<theme words>] [--model single|double|boss|matched|horde]… [--accept [--pick N]]`, `lib/domains/encounter-catalog/build.ts`, `cli/rpg/sim/build.ts`): the Monster Vault's encounter models filled from the bestiary by role and sized to the party's benchmark, each simulated; the fitting ones best first, at most two a model; the GM names them and writes the scene; `--accept` keeps one in the catalog as a draft tagged `built`. `rpg sim homebrew "<base>" --name "<new>" [--role R] [--template T] [--cr C] [--type T] [--habitat H] [--write]` (`cli/rpg/sim/homebrew.ts`) makes a creature from a statblock: reflavoured, a role template (the `Role (…)` template note applied like any other, the role written), a new CR (HP and AC by the CR table; plain-text damage reported, not rescaled); `--write` writes `<system>/worldbuilding/bestiary/homebrew/<name>.md` as a draft. `--template <name> [--choose <option>] [--trait "<feature>"]…` applies a creature template (Zombie, Shadow, Dragon Lich, Fey Champion… the notes in `<system>/worldbuilding/bestiary/templates/`, read by `lib/domains/statblocks/monster-template.ts` and applied by `apply-template.ts`: the Statistics lines carried out, the features added as refs to `worldbuilding/traits/features/Monster Template Traits.md` with the book's bracketed formulas worked out for the creature, what needs a person under `byHand`); `rpg sim lineages [--write [--force]]` makes lineages templates of kind `lineage` for "Humanoid (Any Lineage)" NPCs (`lib/domains/statblocks/lineage-template.ts`: the Monster Vault's NPC Features rows, features taken from each humanoid's statblock; the lineage notes' traits reworded into `Lineage NPC Traits`; each block (`id: npc`) at the end of the lineage's own note, which a list of lineages leaves out with the call option `.omit(npc)` (`lib/domains/references/omit-fences.ts`), a humanoid with no lineage note in `bestiary/templates/lineages/`; a Lycanthrope's "choose a Humanoid" takes one: `--choose elf`). `rpg sim templates ["<base>"] [--write [--force]]` lists them, which fit a creature, and writes that features note and each template note's `rpg stat.template` block (`lib/domains/statblocks/template-block.ts`: the changes as data). In Obsidian that block is the **template sheet** (`lib/components/statblock-template.tsx`: the changes, and Try on: the template on any bestiary creature, changed values marked, Save as homebrew). **Summons** are `rpg stat.summon` blocks (`lib/domains/statblocks/summon.ts`, `formula.ts`, `lib/components/statblock-summon.tsx`): stats and features with `{{ formulas }}` over params (a spell's circle, the summoner's `pb`, `level_<class>`, `mod_<ability>` read from a character note by `lib/services/creature-notes.ts`), forms, a thrall (`apply:` a template to a bestiary creature); each number shows its formula on a tap. See `docs/encounter-catalog.md`.

**Monster roles** (`lib/domains/encounter-sim/monster-role.ts`, `statblock-role.ts`, `cli/rpg/sim/roles.ts`): controller, leader, soldier, striker (Monster Vault, "Monster Roles and Tactics"), each with subroles (controller hexer|disabler|zoner|mover; leader commander|healer|warder|summoner; soldier rank-and-file|guardian|brute|pinner; striker bruiser|skirmisher|ambusher|artillery|solo) and tags outside the tree (flier, caster, legendary, swarm). Written in a statblock as `role:`/`subrole:` or guessed from it (HP, AC and damage per round against the Homebrewer's Toolbox CR table, features, a name that says it; the role scoring is kept as the owner reviewed it, the subrole signals never move the role). `rpg sim roles` lists them (read-only; `--write` writes guesses at or above `--min-confidence`, `--set "<note>=<role>/<subrole>"` writes corrections); `rpg sim equivalents "<note>"` lists monsters of its role within `--steps` (1) of its CR, the same subrole first, another family first. An unsure guess (margin < 0.5) is decided by signature rules (`SIGNATURES`, a `rule` on the guess); `roles --confidence low --features` prints a dossier to review the rest. The statblock header shows the role as a small ribbon in the plugin's own role colours (`--rpg-role-*` in `statblock.css`), the type line the subrole (a name too long to share the bar moves the chip to the type line); a guess is a dashed tint with "?", shown per the `statblockRoleGuesses` setting; tapping the chip opens its meaning (`StatblockMonster` props `role`/`subrole`, passed by the vault's system).

**Single-block notes** (`lib/domains/notes/single-block.ts`, `lib/plugin/single-block-title.ts`): a note whose first thing after its `# heading` is its only `rpg` block, of a kind that prints its own name (`stat.*`, `item.*`, `spell`, `feature.*`), hides that heading (and the inline title and embed title) in reading view, hover previews and embeds; lore after the block is fine, an introduction before it keeps the title. Setting `hideSingleBlockTitle` (on).

## rpg-dev CLI (DevTools Automation)

A CLI at `cli/rpg-dev.mjs` wraps the Obsidian CLI to automate debugging and inspection. Requires Obsidian running with `testing-vault` open.

- `node cli/rpg-dev.mjs compile-html -i <path>` — Extract rendered HTML fragments from Obsidian reading mode
- `node cli/rpg-dev.mjs capture-logs -i <path>` — Capture console output after page render
- `node cli/rpg-dev.mjs css-report -i <path>` — Generate computed CSS snapshots per `.selectors` companion file
- `node cli/rpg-dev.mjs dom-snapshot -i <path>` — Capture structural DOM tree as YAML
- `node cli/rpg-dev.mjs perf-timing -i <path>` — Measure post-processor render timing
- `node cli/rpg-dev.mjs state-inspect -i <path>` — Dump KV store + frontmatter state

**When to use:** After CSS/component changes to verify rendering, when debugging layout or style issues, when investigating why a block doesn't render, or to create regression baselines. Use the `/rpg-dev` command for detailed guidance.

**Key facts:**

- Input paths are relative to plugin root (e.g., `../testing-vault/Sandbox/Tests/03-TEST-SKILLS.md`)
- Output goes to `tmp/rpg-dev/` (gitignored)
- All commands auto-unfold collapsed sections before capture
- Obsidian virtualizes DOM sections — extracted HTML is viewport-limited
- `.selectors` companion files live next to `.md` files for `css-report`
